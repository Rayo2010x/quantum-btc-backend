> **Status:** DRAFT

## 1. Purpose and Scope
This document establishes the aesthetic, functional, and security guidelines for any user interface (UI) or web client developed for **QuantumBTC**. Its main objective is to ensure that all interfaces are professional, secure by design, and avoid using generic or predictable designs frequently generated by artificial intelligences, prioritizing a bold aesthetic stance and ironclad security.

## 2. Fundamental Directives
Any frontend development must be governed by the following principles, in order of priority:

1. **Secure by Design:** The UI is not just presentation; it is the first line of defense. Security precedes aesthetics.
2. **Functional Clarity and Accessibility:** Predictable, unambiguous, and equitable interfaces for all users.
3. **Aesthetic Quality (Anti-Generic):** Professional, cohesive, and bold designs, avoiding boilerplate templates and repetitive visual solutions.

## 3. Interface Security (Mandatory)
In strict alignment with the global security directive (Global Security & Professionalism Directive Section), every frontend component must implement:

- **Rigorous Sanitization and Validation:** Strict client-side validation (in addition to mandatory server-side validation) for all user input to prevent attacks such as Cross-Site Scripting (XSS).
- **Secure Credentials and Sessions Handling:** Do not store sensitive tokens (e.g., highly confidential JWT Tokens) permanently and vulnerably in `localStorage`. Apply `HttpOnly` and strict domain controls when interacting with the backend.
- **Error Handling Exposure Control:** Ensure visual feedback (alerts, toasts, form errors) does not expose technical or infrastructure information or confidential server logs to the end user.
- **Protection against Spoofing/Clickjacking:** Establish preventive policies in conjunction with the backend (e.g., `Content-Security-Policy`, `X-Frame-Options` headers).

## 4. Aesthetic and Visual Guidelines

### 4.1. Typography
- **Prohibition of Cliched Fonts:** The default use of generic and overused fonts like Arial, Inter, or Roboto is discouraged unless the component requires it for strict utilitarian legibility.
- **Deliberate Selection:** Choose paired typographies with personality: a strongly distinctive Display font accompanied by a refined font for the body text.

### 4.2. Color Palette
- **Thematic Cohesion (Vibe/Aesthetic):** The design must commit to a clear base aesthetic (e.g., luxurious dark, brutalist minimalist).
- **Prohibition of Default Colors:** Avoid using default browser blues, reds, or greens. Any palette must use harmonic and curated tones (e.g., schemes based on HSL values or well-constructed CSS variables).
- **Accessibility and Contrast (a11y):** Guarantee a minimum required contrast (WCAG AA or AAA) for legibility. If the design feels monotonous, apply layers of light/shadow instead of losing homogeneity.

### 4.3. Composition, Layout, and Spacing
- **Spatial Design and Depth:** Provide generous and rhythmic negative space (whitespace). Avoid "crowded box density".
- **Bold Structures:** Allow moderate experimentation with asymmetry, overlaps, or layouts that break the grid when they benefit the screen's narrative flow, without sacrificing UX.
- **Details and Textures (Micro-aesthetics):** Apply smooth noise textures or patterns, subtle gradient meshes, or high-quality _glassmorphism_ effects where it increases user immersion.

### 4.5. Movement and Micro-interactions (Motion)
- **Structural Use:** CSS animations and transitions must be used intentionally to a) orient the user and b) provide tactile feedback, not just as "blind embellishment".
- **Staggered Reveals:** Encourage content to land with staggered and smooth animations on initial load to avoid abrupt and disorienting changes.
- **CSS Optimization:** Prioritize pure and hardware-friendly CSS solutions before massive JavaScript dependencies for common effects (e.g., dynamic hover states and spatial transformations).

### 4.6. Verification Page (Provably Fair UI)
- **Aesthetic of Truth:** This section should feel like a "Technical Laboratory". Use monospaced fonts for data values (hex strings, hashes) to emphasize precision.
- **Interactive Breakdown:** Use a "Conveyor Belt" or "Mixing Tank" diagram or animation to show how the four inputs (Client, Server, Quantum, Public) fuse into the final result.
- **Trust Indicators:** 
    - Use green "Verified" badges when a calculation is validated locally.
    - Provide deep links to external explorers (drand) to demonstrate the absence of collusion.
- **Copying Experience:** Guarantee all hexadecimal strings have "Click to Copy" functionality with subtle visual feedback.

### 4.7. Unified Social Footer
- **Brand Consistency:** All satellite projects and web applications associated with QuantumBTC (including `quantumbtc.dev` and `learn.quantumbtc.dev`) must implement a unified footer.
- **Standard Structure:** The footer must display the copyright text on the left ("© 2026 QuantumBTC...") and a block of research social links on the right with the text "You can contact us and/or follow our research at:" accompanied by five interactive vector icons: Nostr, X, Discord, Telegram, and GitHub.
- **Objective:** Reinforce cross-visibility of our research regardless of the user's entry portal.

### 4.9. Responsive Navigation
- **Desktop (≥768px):** Render a horizontal tab bar with all five navigation items visible inline: White Paper, Roulette, Statistics, FAQ, Verify (Fair) & History.
- **Mobile (<768px):** The tab bar collapses into a hamburger button (☰) anchored to the right side of the header. Tapping it toggles a full-width vertical dropdown panel showing all five navigation items as stacked buttons.
- **Implementation Constraints:**
  - All navigation items MUST remain as `<button>` elements in the DOM at all times (never use `<select>`) to preserve crawlability and accessibility.
  - The dropdown must close automatically when any item is selected.
  - Keyboard accessibility: the hamburger button must be reachable via `Tab` and activatable via `Enter`/`Space`.
  - The active view must be visually differentiated in both desktop and mobile states using the `text-primary` colour token.
- **SEO:** No negative SEO impact; all navigation buttons remain rendered in the DOM.

### 4.8. Technical SEO and Meta-tags
- **Canonicalization:** To avoid duplicate content errors ("Duplicate without user-selected canonical" in search consoles), the main landing page and any other generated static route MUST explicitly declare their canonical URL.
- **Home Implementation:** For the root of the Single Page Application (SPA), the strict canonical URL is `<link rel="canonical" href="https://quantumbtc.dev/" />`.

## 5. Implementation Process and Definition of Done

According to the project's central documentation paradigm (`quantum-btc-backend`):
1. **The Component as a Documented Unit:** Prior to implementing a component or main view, the UI/UX approach must be logically described or referenced.
2. **Component Security Review:** All critical visual implementation (e.g., payment forms, wallet login) must be explicitly validated from a preventive security perspective prior to any "merge".

---

> **Change Control and Exceptions:** Any temporary deviation from this guide due to unavoidable technical limitations (legacy packages, framework limits, etc.) must be documented, always prioritizing stability and the "Secure by Design" rule over visual sophistication.
